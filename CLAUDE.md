# Helios & Selene — Project Memory

A companion puzzle-adventure to *What the Snow Remembers* (github.com/chien521/What-the-Snow-Remembers) — same engine and tone, standalone codebase, different mechanic and myth. Built with GitHub Copilot doing the primary implementation; Claude Code assists on debugging, architecture review, and structural work.

## Stack

Three.js + Vite, vanilla ES modules, browser-only, no backend required for core gameplay. New standalone repo — not a branch or folder inside What-the-Snow-Remembers.

`npm run dev` (Vite), `npm run build`, `npm run preview`. No tests, no linter, no CI.

## Status (verified by scripted playthroughs of both chapters)

- **Helios is complete and winnable end to end.** Five puzzle beats, five traversal legs, no console errors, no softlocks found.
- **Selene is complete.** `chapters/selene.js` now carries a full `layout`: a crater descending from the hub to still water, with a moon-phase dial box, three phase surfaces, a moonwell relay chain and a doorway in the water. `buildSeleneRoom()` is gone, and with it the `layout`-or-fallback branch in `ChapterLoader.load()`.
- Finishing Helios now shows a **chapter-complete beat** (`#chapter-complete`) before Selene loads, instead of swapping chapters mid-frame. Completion still persists in `localStorage['helios-complete']`.
- Verification is by script, not by hand — there is still no test runner. Two throwaway Node scripts were used and are worth rebuilding if the layouts change: one re-derives Selene's geometry (moonline, jump margins, whether the pool chain has a solution) from `selene.js`, the other runs the real `ChapterLoader` over both chapters behind a stubbed `document`. A Playwright script drives the whole of Selene through the DOM by reading `#scope-label` / `#moon-phase`.

## Premise

A nameless traveler carries an unfinished telescope through two worlds that can never share a sky: **Helios** (the sun's domain) and **Selene** (the moon's domain) — two figures who love each other but were never in the sky together. The traveler is building a way for them to finally be seen together, once, through a telescope completed from one lens found in each world.

In player-facing copy the one instrument is now given two names depending on which world it's raised in — `MAGNIFIER` in Helios, `TELESCOPE` in Selene (`main.js:398`) — but this is copy only, not an architecture change: there is still exactly one `Telescope` state object (`src/world/Telescope.js`), carried from Helios into Selene via `telescope.carryFrame()`. Don't go looking for a second instrument class.

No dialogue, no named traveler, no explanation during play — wordless, first-person-passage storytelling, same as Seasons. The myth is told in full only once, at the very end: a full ~380-word third-person passage (already written into the `#ending` screen in `main.js`), not a couplet — it still closes on the original two-line couplet ("Helios crossed the day... / ...For one looking, they were together.").

## Core Mechanic — as built

Base verbs: **move (WASD), jump (Space), raise/lower instrument (R — reads as MAGNIFIER in Helios, TELESCOPE in Selene, same key and same underlying state), interact (E), cycle dial (Q), hint (H), pause (Esc)**.

Three design claims from the original spec were **deliberately reversed during implementation** — do not "restore" them without re-reading the rationale comments in `Telescope.js` and `TelescopeAim.js`:

| Original intent | What ships | Why |
|---|---|---|
| Raising the telescope locks movement | Movement stays free while raised | The player commits by *walking* to a mirror, not by freezing the camera (`main.js` comment above `nearestMirror`) |
| Burning-glass hold duration scales with the colour grade, doubling as a difficulty curve | Flat `FOCUS_SECONDS = 1.15` | "Duration is only difficulty when something can go wrong during it, and nothing could." Difficulty now lives in mirror-chain length |
| Telescope focus is the puzzle | Focus is *confirmation*; the puzzle is routing sunlight | The old hold-to-charge system was a loading bar, and was the chapter's only verb |

**Helios's actual puzzle language: route sunlight, then confirm with the scope.**
- `SunBeam.js` traces 2D rays breadth-first, max chain 4. A mirror standing inside a `lightZones` x-range (was `sunlitZones`; Selene uses the same field for moonlight) is lit and throws a beam **along the direction it faces** — deliberately not physical reflection, because "the mirror sends light where it points" is readable in one glance.
- `Mirror.rotate` ping-pongs within its `arc` at `TURN_SPEED = .9` rad/s while E is held and the player is within 2.6 units.
- Raising the scope and holding LMB on a target for 1.15 s produces a `focusedTarget`. Only then do the receivers the beam currently touches `latch()` (permanently, turning red and scaling 1.35×).
- Hit radii are **gameplay values, not visual ones**: `MIRROR_RADIUS = 1.1`, `RECEIVER_RADIUS = .7`. At ~12 units these give roughly a ±0.05 rad aiming window — tune against `TURN_SPEED`, not against mesh size.

**Selene's puzzle language: turn the moon, and the crater rearranges.** The exact inversion — Helios's scope *confirms* a routing the player already set up, Selene's scope *acts*.
- Holding focus on the moon for the same `FOCUS_SECONDS` advances its phase, `new → full → waning → new`. Phase is one global piece of state.
- A platform declares a `phase` and is solid only during it. No `phase` means stone: solid always, and **the only kind that can hold a checkpoint** (`platformAt` skips phase surfaces, or a respawn would drop the player into air).
- **The moonline is the whole difficulty curve.** The moon is focusable exactly while it is on screen, which `TelescopeAim.hovers` already enforces, so with the camera at `player.y + 5` and ~11.33 units of half-height it reduces to `surfaceY > moonY - 17.43`. With the moon at y=4 that line sits at −13.43: `brink` (−10) is the last place you can turn the dial by looking up. Everything below is entered on a phase chosen before the drop. **Move a platform across that line to change a beat's difficulty; do not add gates.**
- **The grace rule:** the platform the player is standing on stays solid through a phase change and goes intangible when they step off (`setPhase(phase, groundedPlatform)` / `releaseHeld`). Turning the dial can cost you a route, never a fall — that is what keeps Selene as failure-free as Helios.
- Out-of-phase surfaces are ghosts while the scope is raised and invisible while it is down, so raising the scope is how you *read* the room. Ghost opacity is `.36`; `.17` was invisible against the crater's sky in play.
- Below the moonline the **moonwell chain** buys the phase back: a fixed relay (`arc: null`) standing in `lightZones` feeds a rotatable pool, which the player sweeps with E onto a `hold: true` receiver. A hold receiver is lit only while a beam is actually on it, and is a focus target while lit. This is the only place Helios's mirror verb returns, inverted: Helios sends light *out* to a target, Selene brings the moon *in* to where you stand.

## The Object — Split Lens

Helios yields **two parts**, not one (HUD reads `PARTS n / 2`):
1. **Telescope frame** — reward for the 3-dial lockbox. Calls `telescope.unlockAim()`, which switches the whole optical layer on (`updateBeams({ visible })`). Without it, no mirrors, no beams, no scope.
2. **Helios lens** — reward for the 4-dial lens box. Calls `telescope.unlock('helios')`, which is what gates `meltBridge` and `exitBridge` into `focusTargets`. The back half of the chapter is mechanically unsolvable before it, as intended.

Selene yields the other two, and reuses the same two flags (`state.frameCollected` / `state.lensCollected`) so the HUD stays chapter-agnostic:
1. **Moon lens** — reward for the 3-dial phase box. Calls `telescope.unlock('selene')`, which is what makes the moon a focus target at all. The whole crater below the lockbox is unsolvable before it.
2. **Eyepiece** — on the tide ledge at the bottom. Collecting it completes the telescope and reveals the doorway in the water.

The generic `fragments` ring collectibles are gone; both chapters now use frame + lens.

## Chapter 01 — Helios, verified walkthrough

Authoring lives in `chapters/helios.js` so tuning is a one-line data change. Room shape: a **hub** at y=0, a **climb** ledge (+1.5) and **vista** (+3) to the left, a **pit** floor at y=-9 below, and a right-hand aerial route at y≈8.5.

1. **Hub → climb ledge.** Run-jump left across a 2.5-unit gap / 1.5 rise (the recurring margin; jump apex is 1.92, so it is comfortable, not tight).
2. **Lockbox (3 dials: sun / star / moon).** Hint via H: *"He rose alone… / a thousand small witnesses / She came after, wearing what light he left behind."* Q selects, E turns. Opening reveals the mirrors chapter-wide and drops the **frame**; collecting it pans the camera to the heliostat.
3. **Vista → heliostat.** One rotatable mirror at (-25, 4.6), arc [0.6, 2.4], sitting inside the only light zone (-30…-18). Note this leg has to be *jumped* (2.5 gap over a 1.5 rise) — walking off the climb ledge drops into the void and respawns.
4. **Two sky receivers.** Aim ≈1.819 rad for `sky-west`, ≈1.281 rad for `sky-east`; hold focus on the *mirror* (not the dot) for each. Both latched ⇒ the lens box reveals and the camera pans to the pit.
5. **Pit → lens box (4 dials: fire / wind / dust / ice).** Hint: *"could not be held / could not stay / could not remember / could not forget."* Opening reveals the **lens**.
6. **Springs.** Two, at the right edge of the pit floor and of the hub. There is **no step-up in the collision resolver**, so a spring cannot be walked onto — it must be jumped onto. There is also no horizontal momentum (`vx` is rewritten from the input axis every frame), so a mid-air burst is a pure position offset.
7. **Burn the floating wall.** Scope up on the hub, hold focus on the wall at (13.5, 11.1). It vanishes and leaves a walkable deck at y=8.55; the exit reveals and a **sky marker** appears at (16, 20).
8. **Marker → exit bridge.** The marker is only on screen from the melted deck (the camera sits at player.y + 5 with ~11.3 units of half-height), so this beat is correctly sequenced by altitude.
9. **Exit.** Walking the bridge with the scope **raised** pulls the doorway from x=42 in to x=26.8; `finishChapter()` fires when raised *and* within 2 units. The door now starts hidden and is revealed by the burn.

## Chapter 02 — Selene, verified walkthrough

Authored in `chapters/selene.js`. Shape: a **crater**, deliberately not rhyming Helios — it descends from the shared hub (y=0) to still water at y=−30, zigzagging inside x −12…18. The zigzag is not decoration: the moon has to stay within ~14 units of anywhere the player stands or the reticle cannot reach it (~15 units of camera half-width at 4:3).

Spawn is `(2, 1.1)`, set by `chapter.spawn` — Selene opens with the telescope already carried out of Helios (`telescope.carryFrame()`: `aimUnlocked` true, `power` null), so raising it ghosts the phase surfaces while focusing the moon does nothing.

1. **Lip → shelf.** Gap 2, drop 3 — a fall, where Helios's opening is a run-jump *up*.
2. **Phase box (3 dials: new / full / waning).** Hint: *"She showed nothing, and was still there. / She gave back all of it, and kept none. / She turned away by the width of one night."* Solution `['new','full','waning']` is **also the order the sky dial cycles in** — the box is the manual for the verb. Opening drops the **moon lens**; collecting it calls `telescope.unlock('selene')` and pans to the moon.
3. **First turn.** Moon plainly on screen. One focus: `new → full`, and the silver ledge becomes solid. Gap 1.5, drop 3.
4. **Silver → brink.** Gap 1.5, drop 4. `brink` (−10) is the last platform above the moonline.
5. **Commit.** Two turns (`full → waning → new`) *before* dropping left onto `shade` (−15), which is below the line. Guessing wrong is not a failure: the fall continues to `pool-shelf` (−23) and costs a detour, nothing else.
6. **The moonwell chain.** `moonwell` is a fixed relay at (1, −21.9) standing in `lightZones: [[0, 2]]`, always lit — at this depth the moon is not overhead any more, it is in the water, so the light enters from below rather than through a shaft. `pool` at (4, −20.5) is the one rotatable mirror, turnable from `pool-shelf` and deliberately **not** from a phase surface, so the chain can never be stranded behind the phase it is meant to fix. Sweep it to ≈ 0.01 rad (window 0.140 rad) to land the beam on `moon-dial` at (14, −20.4). Focus the lit dial to turn the phase from under the line. The dial sits above head height on purpose: at standing centre the player walks into it and occludes the one thing they need to read.
7. **Tide → eyepiece.** Two turns (`new → full → waning`) makes the tide ledge solid; the **eyepiece** sits on it and is visible from the moment the crater opens up, the way Helios's sky marker is. Collecting it reveals the doorway. The one spring, at x=−11 on the water, is the way back up if it is missed — that is the only column in the crater with no ceiling over it.
8. **Exit.** The moon's reflection, half-drowned in the water at x=8. Holding focus **rises** it toward you and looking away sinks it — the inversion of Helios's door, which comes to you for walking at it with the glass up. `finishChapter()` needs both the completed hold and `reached` (radius 2).

Three constants in the crater are gameplay values with derivations, not art direction. Changing any of them without redoing the arithmetic breaks the chapter:

- **The exit's rise is capped by the reticle.** The door is the thing the player holds the reticle on, and the door moves. `SPOTLIGHT_RADIUS` is 72px and one world unit is ~32px at this camera, so a rise past ~2.2 units walks out from under its own reticle, cancels the focus and sinks again — an unwinnable ending. It ships at 1.2.
- **The tide ledge is a thin slab (`h: .8`).** Platform boxes are 2 deep by default, which over the water at −30 leaves 1.5 of headroom — less than the player's 2.2 — so the ledge becomes a wall across the water floor and pens the player away from the doorway. Any platform authored *over* a walkable floor needs this check.
- **The pool's aiming window is 0.138 rad**, from `RECEIVER_RADIUS = .7` at ~11.5 units, i.e. ~0.15s of sweep at `TURN_SPEED = .9`. That is deliberately in the same range as Helios's heliostat beat. Tune it against `TURN_SPEED`, not against mesh size.

## Visuals

`palette.open / mid / close` is used **two ways at once**, which is easy to trip over:
- as a fixed **vertical sky gradient** painted to a canvas texture (open at top → close at bottom), so all three stages are on screen simultaneously; and
- as a **progress lerp** driving the directional light, hemisphere light and fog. Helios reads that progress across **x** (orange left climb → white summit); Selene sets `gradeAxis: 'y'` and reads it **down** (pale at the lip → deep navy at the water), because its journey is a descent.

The `Moon` uses `MeshBasicMaterial` for both its disc and its shadow, unlike everything else in the scene. It is a light source and must read identically at the pale lip and in the navy depths; lit materials get dragged around by `updateGrade`'s hemisphere and directional colours, which made the full moon come out a dull grey exactly where it should be the brightest thing on screen. At `full` the shadow disc is **hidden**, not slid aside — any offset big enough to clear the face left it sitting inside the halo as a second, black moon.

`darkShade()` derives shadow tones in sRGB channel space on purpose — a plain `multiplyScalar` on a `THREE.Color` reads ~3× brighter than intended after gamma correction. Non-stone objects (springs, ladder wall, etc., still `MeshBasicMaterial({ color: this.shadow })`) are near-black by design. **Stone platforms are the one exception as of the Downloaded art pass below** — they moved to a brighter `darkShade(..., .3)` tint so a texture would show; see that section before assuming "near-black" still applies to platforms specifically.

| Stage | Colour |
|---|---|
| Helios open / mid / close | `#ff8c1a` / `#f5d9a8` / `#f5f0e6` |
| Selene open / mid / close | `#dceffa` / `#9ce6f7` / `#36577d` |
| True ending | deep navy + one small saturated orange source (CSS `.end-image`) |

### Downloaded art (new — first object swapped away from pure primitives)

Everything up to this point was raw Three.js primitives/procedural canvas textures, no downloaded files. That's changing object-by-object, at the user's request, toward a painterly/soft-realism direction — starting with the **player rig**. Each swap is picked and confirmed with the user individually before being wired in, so don't assume the rest of the primitive objects (Mirror, Moon, Lockbox, platforms, etc.) are next just because this one landed.

- **Player** (`src/core/Player.js`) loads `src/assets/models/player.glb` through `GLTFLoader` (`three/examples/jsm/loaders/GLTFLoader.js`, bundled with the `three` package already installed; no new npm dependency). Replaced the original `CapsuleGeometry` mesh entirely at first, then went through one full model swap since — see the "Redesigned" entry directly below for the current model; the two paragraphs after that describe work done on the *original* model that's now superseded.
  - **Redesigned (current model).** Quaternius's "Hooded Adventurer" (CC0, poly.pizza/m/y9KWOVG21R) replaced the earlier "Animated Human" (poly.pizza/m/c3Ibh9I3udk) at the user's explicit request — the old model read as gaunt/hunched and uncanny even after the AI-restyled fabric texture pass below, and a real screenshot comparison confirmed the texture wasn't the problem: the base rig's proportions and single flat-tinted material were. This model ships as several separately-materialed parts (body/feet/head/legs; each already a distinct real color — black, light/dark brown, skin, gold, metal) instead of one flat mesh, so it reads as an actual figure with **no forced retint or texture needed** — the AI fabric texture pass described below is no longer applied to this model (the file, `src/assets/textures/player/fabric.jpg`, is still on disk but unreferenced; harmless to delete if this is ever cleaned up, kept for now in case a future pass wants to texture just this rig's cloth parts).
    - Also a better thematic fit: the source is Quaternius's combat-ready "Adventurer" rig re-skinned with a hood/cloak, and a hood reads as anonymous by design — closer to this game's explicit "no named traveler... wordless" premise than the previous open-faced model.
    - **The source ships a physical sword** (`Sword_1/2/3`, unskinned accessory nodes meant to be visible in its combat idle poses) that has no place in a story with no combat and no weapon anywhere else in its design. `Player.js` filters any node whose name starts with `Sword` out of the scene graph entirely (not just hidden) before the height/Box3 measurement, so no stray geometry lingers or skews that measurement.
    - **This rig has no dedicated `Jump` animation clip** (confirmed by listing `gltf.animations` directly on load, not assumed) — `Roll` is the closest airborne-reading pose it ships, so `Player.update()`'s per-frame `_play(...)` call now requests `'Roll'` while airborne instead of `'Jump'`. Worth remembering for any future model swap: `_play()` silently no-ops on a missing action key rather than throwing, so a wrong animation name doesn't surface as an error, it just never visibly plays — always list `gltf.animations` for a new model before assuming a clip name carries over.
    - `BASE_FACING_Y` (rest pose facing `+Z`, rotated 90° to profile) turned out to already be correct for this model too — verified via screenshot (walking both directions faces the right way), not assumed just because the constant carried over unchanged.
    - Verified in both chapters via real screenshots: reads as a clean hooded silhouette against both Helios's warm grade and Selene's cool one, correct facing-flip on direction change, no console errors, sword confirmed absent.
  - **AI-restyled fabric texture (superseded by the model swap above, kept here for history).** The original "Animated Human" model shipped as a single flat-gray mesh; its material's UV was real and usable — a genuine (if narrow) body unwrap, U spans ~0.46-0.595, V spans ~0.11-0.857, confirmed via `GLTFLoader.parse()` in a standalone Node script, not the degenerate atlas-sliver problem the Lockbox chest had. Was tinted to `#d8d2c4` (a flat warm-parchment tone) with no map at all; later carried an AI-generated fabric texture applied directly through those existing UVs — deliberately not reprojected with `boxProjectUV()` like the chest/gem/spring, since a human rig's real unwrap has per-limb seams a generic box projection would visibly break.
    - **A real "double-multiply" bug shipped on that model and was caught by direct pixel comparison, not assumed fixed.** The first version kept `material.color.set(PLAYER_COLOR)` *and* added the new map — `map * color` can only ever get darker than either alone (texture values are ≤ white), and since `PLAYER_COLOR` was tuned as a complete standalone color for a mapless material, compounding it with the new texture measurably shifted the character from light parchment tan toward a dark rust-brown. Caught by cropping the same screen region from before/after screenshots and comparing mean RGB directly, not by eyeballing. Fixed the same way as the chest: `material.color` set to white so the texture's own color carried the look untouched.
    - **The texture itself also needed a second pass.** v1's generated fabric (mean RGB ~193,169,126) skewed more orange/saturated than the original neutral `#d8d2c4` (216,210,196, much higher blue). v2 pushed the prompt explicitly toward "pale," "neutral," "low saturation" and landed much closer (mean RGB ~192,190,178). `art-restyle-pipeline/workflows/generate_batch2.py` (v1) → `generate_player_fabric_v2.py` (v2). Neither is wired into the current model.
- Model height is normalized to the physics capsule's height (`body.hh * 2`) and its feet aligned to the collider's bottom edge at load time via a `Box3` measurement — this is done dynamically, not by hand-tuning a scale constant, so it stays correct if the source file is ever swapped for a different model. Already proven across two different source models now.
- CC0 needs no attribution, so no credits screen was added. If a future swap pulls in a CC-BY resource (game-icons.net was the one candidate raised during resource research), that changes and needs a credits line somewhere in the UI.

- **Mirror — tried, then reverted at the user's request.** `src/world/Mirror.js` was swapped to load Kenney's "Bathroom Mirror" (CC0) for a session, replacing the flat gold `TorusGeometry` + `CircleGeometry`. Getting there required real work: the first candidate (Poly Haven's "Ornate Mirror 01") had to be abandoned because it's a flat photo-textured plane, and this game's mirrors are mathematically *always* viewed exactly edge-on (`this.group`'s `rotation.x = PI/2` then `rotation.y = angle` composes to a world normal with zero depth-axis component at every angle — verified with `THREE.Euler`/`Quaternion` directly). The Kenney swap worked technically (real volumetric depth, a separate `glass` mesh `setLit()` could tint directly) and was visually verified rendering correctly. **The user then asked to go back to the original small circular mirror anyway** — a pure aesthetic preference, not a bug — so `Mirror.js` was reverted via `git checkout -- src/world/Mirror.js` and `src/assets/models/mirror_bathroom.glb` deleted. The edge-on geometry finding above is still true and still worth knowing before touching this file again, but the mirror itself is back to the original torus+disc. Don't re-attempt this swap without checking with the user first — it was already tried and explicitly turned down once.

- **Moon** (`src/world/Moon.js`) now maps `src/assets/textures/moon.jpg` onto the existing flat `CircleGeometry`/crescent `ShapeGeometry`, reusing the same texture across all three phase modules via `MeshBasicMaterial`'s `map * color` multiply. A lit `SphereGeometry` + HDRI was the original plan (per the resource shortlist) but had to be dropped: the Moon is deliberately `MeshBasicMaterial` (unlit) specifically so it stays grade-immune (see the "dull grey" bug note above) — a lit sphere would reintroduce exactly that bug, and a sphere buys nothing visually anyway once the material is unlit (no normal-based shading either way, so a textured flat disc and a textured sphere render identically from a fixed camera angle). Phases are told apart purely by `material.color` tint (`NEW_MOON` for `new`, `FULL_MOON` for `full`/`waning`) over the same crater detail. The `waning` crescent's `ShapeGeometry` needed its UVs recomputed by hand in `crescentGeometry()` (`u = (x/radius+1)/2`, matching `CircleGeometry`'s own convention) — three.js doesn't guarantee a custom `Shape`'s auto-UVs line up with a texture the way a primitive's do.
  - **AI-restyled (third texture through the ComfyUI pipeline).** The original was NASA LRO's "Moon Mosaic" (public domain, svs.gsfc.nasa.gov/5001) — a real satellite photo mosaic with visible blocky tile-seam artifacts from the stitching. `art-restyle-pipeline/workflows/restyle_moon_color.py` runs it through img2img twice: a first pass at `denoise .5` kept the seams intact (SDXL preserved that low-frequency block structure) and leaned photographic despite the prompt; the shipped version is a second pass at `denoise .78` with a more insistent "matte painting / gouache / visible brushstrokes / no photographic detail" prompt, which both removed the seams and reads as genuinely painterly. Composition (mare/crater placement, disc filling the frame edge-to-edge) is preserved well enough to still read as the same moon, though not pixel-identical — expected and fine at this denoise.
  - **A constraint the other two restyled textures didn't have, and had to be actively checked for, not assumed:** `Moon.js` multiplies this map by `material.color` per phase (`NEW_MOON` near-black navy, `FULL_MOON` warm cream) to tell phases apart, since the material is deliberately unlit. If the restyled texture picks up its own hue, that multiply muddies instead of cleanly tinting. Both the prompt (explicit "grayscale"/"monochrome") and negative prompt (explicit "no color") targeted this, but was **verified numerically, not eyeballed**: sampled RGB channel deviation across the full image averages 2.1/255, with only ~0.1% of pixels (a handful of small bright specular flecks, an SDXL artifact on tiny highlights) showing any real color cast — close enough to neutral gray that the phase-tint multiply still works as designed. Any future restyle of this specific file needs the same check (a quick per-pixel max-channel-diff script, not a glance at the thumbnail) before being treated as safe to ship.
  - **Since verified live in-engine, all three phases, by actually solving the puzzle** — not a shortcut this time. Scripted the real dial sequence (`dials` starts at `(index+1) % glyphs.length` per ring, each `E` press advances the selected dial by one glyph, `Q` moves selection — solving `['new','full','waning']` from that starting state took two `E` presses per dial), collected the moon-lens reward to unlock `telescope.power`, then held focus on the moon three times to cycle all phases, screenshotting each. All three read correctly: near-black new moon, warm-gold full moon with real painterly crater detail visible, and a correctly-shaped waning crescent — confirming the grayscale check above was sufficient and the phase-tint multiply works as designed.
  - **A real headless-browser gotcha hit during this verification, worth remembering for future scripted QA in this repo**: holding the mouse down via Playwright and just `waitForTimeout`-ing past `FOCUS_SECONDS` (1.15s) did not work, even with several seconds of margin — the focus charge never completed. The cause wasn't game logic; `frame()` in `main.js` clamps each frame's delta to `Math.min(clock.getDelta(), .05)`, and headless Chromium's `requestAnimationFrame` appears to get heavily throttled during a plain blind wait with no other CDP activity, so very few frames (each capped at .05s of simulated time) actually fire regardless of real elapsed time. Confirmed by polling the charge bar's `transform` style via `page.evaluate()` every 200ms during the hold — progress climbed steadily (interacting with the page via `evaluate`/`textContent` calls seems to force real frames through), where a blind `waitForTimeout` alone made almost no progress. **Fix for any future scripted hold-to-charge interaction**: poll a visible state change (the charge bar, `#moon-phase` text, etc.) in a loop with short waits between checks, rather than one long blind wait — it's not just more reliable, it's what makes the underlying animation actually run.

Loading it the normal way (even with `SkeletonUtils.clone()` — the standard three.js fix for cloning rigged glTF assets so each instance doesn't share one skeleton) produced a bounding box roughly 200 units across, lying sideways along world Z instead of standing on Y. This was **confirmed by direct measurement**, not guessed: a standalone Node script (`GLTFLoader.parse()` on the raw file, no browser/DOM needed) printed the loaded scene's `Box3` and showed exactly this — `y: -110..110`, `z: -193..0.3`. Cross-checked against the raw glTF JSON (`skins[0].joints` pointing at nodes under a *different* branch than the mesh node itself, each independently scaled) confirmed the cause rather than leaving it a mystery.
  - **Fix**: skip the node hierarchy and skin entirely. `loadSpringModel()` resolves to the two raw `Mesh` nodes (`traverse` + `isMesh`), and `addSpring()` extracts each one's `geometry` fresh, rebuilds them as plain (non-skinned, non-animated) `THREE.Mesh`es under a new `Group`, and rotates that group -90deg about X to stand the source file's Z-up local space onto the game's Y-up convention *before* measuring — re-verified with the same standalone-script technique, giving a sane ~0.02-unit raw box in the expected proportions. No animation plays as a result (nothing in this codebase currently triggers a bounce clip on launch anyway, and wiring one up would mean touching `main.js`'s per-frame update loop, out of scope for this pass).
  - The two source materials are named `Metal` and `Red` (a classic cartoon coil-and-cap bouncer) — recolored to the spring's existing amber palette (`#e8d8ae` base / `#ffb347` emissive) rather than kept literally red, to stay in Helios's warm palette instead of introducing an unrelated hue.
  - **AI-restyled — `Metal` mesh only.** These meshes ship with no UV attribute at all (confirmed the same way as everything else in this pass, `GLTFLoader.parse()` in a standalone Node script), so `boxProjectUV()` builds one from scratch before an aged-bronze metal texture (`src/assets/textures/spring/metal.jpg`) is applied. `Red` (the emissive cap highlight) stays procedural, same reasoning as the gem's crystal facets. **First generation attempt used the word "coil" in the prompt and SDXL literalized it into a bold decorative spiral/rosette wallpaper pattern** — completely wrong for a surface material, caught before wiring it in by just looking at the generated image rather than trusting the prompt intent. Fixed by dropping "coil"/"spring" language entirely (the coil *shape* already comes from the mesh geometry; the texture only needs to be a plausible flat metal surface) — `art-restyle-pipeline/workflows/generate_batch2.py` (v1) vs `generate_spring_metal_v2.py` (the fix). **Honest limitation**: the object is small enough on screen at normal gameplay distance that the applied texture reads as barely distinguishable from the old flat color — confirmed by cropping/zooming a real screenshot, not assumed. The code path is correct and consistent with the other objects in this pass, but this specific swap has low practical visual payoff; not worth further iteration unless the spring is ever viewed larger/closer than it currently is.
  - Synchronous placeholder: a plain `CylinderGeometry` sized to `SPRING_TARGET_HEIGHT` (1.06, matching the old cap-top height) is added to the spring's group in the same frame as construction, and removed only once the real model is built and added — same "transparent box" lesson as Lockbox's chest, applied here since a spring can be `revealed: true` (or revealed mid-play) before the async load resolves.
  - **Lesson for future model swaps**: when an async-loaded object silently doesn't appear (or appears wrong) and nothing in the browser console explains it, a standalone Node script that calls `GLTFLoader.parse()` directly on the `.glb` file and prints `Box3`/node/skin data is faster and more conclusive than screenshotting guesses — it isolates loader/asset problems from rendering/scene-graph problems (the `PeriscopeExit` bug above) without a browser in the loop at all.

- **Burn wall** (`LensGates.createMeltBridge()`, the standing rock Helios's burning glass melts) originally shared `ChapterLoader`'s ambientCG "Plaster001" stone material (see Stone platforms above) instead of a flat `MeshStandardMaterial({ color: shadow, ... })`. `ChapterLoader.addPlatform()`'s texture-building code was pulled out into a `stoneMaterial(w, h)` method so both platforms and the wall could build the exact same textured material rather than duplicating the clone/repeat logic; `createMeltBridge()` takes an optional `wallMaterial` param and falls back to the original flat box if none is given, so the function still works standalone. **As of the AI-restyled-textures pass below, the wall no longer shares the platform's texture** — see the new bullet under "AI-restyled textures" for why; `stoneMaterial()`/`burnWallMaterial()` are now two separate methods on `ChapterLoader` but the same `wallMaterial` plumbing into `createMeltBridge()` still applies, just fed a different material. A light emissive tint (`glow`, lower intensity than before since the texture now carries the visual detail) is layered on top either way, the last remnant of the old "glowing gate" look. The bridge deck the wall melts into is **not** re-textured — it is a distinct post-melt surface, not standing rock, and keeps its original flat warm-brown material.

- **Receivers considered, left as primitive.** `Mirror.js`'s `Receiver` class (the sky-west/sky-east latching dots in Helios; Selene's `hold`-type moon-dial receiver, where that layout exists — see the note below) is a fully separate class from `Mirror` itself, with its own geometry-building code, so the hard constraint against touching the mirror's geometry does not block it. It was still left as a primitive `SphereGeometry` (+ `TorusGeometry` ring for `hold` receivers) after evaluation: at its default size (`size = .24`, latched scale 1.35x) and typical viewing distance (Helios's sky receivers sit at y=16-18, well off the ground path, seen from many units away), a downloaded model would read as an indistinct blob at best — no more legible than the current glowing sphere, for real integration cost (async load, placeholder, license check). The object's entire design intent is also explicitly minimal ("a colored glowing point that turns red when latched," matching the "readable in one glance" standard `Mirror.js`'s own comments set for the mirror itself) — a more detailed model would work against that, not for it. Revisit only if a receiver is ever placed close enough to the player's path that its detail would actually be seen.

- **Note on Selene's crater layout and this pass.** `src/chapters/selene.js` as it stands does **not** currently contain the moonwell/pool/moon-dial chain, `brink`/`shade`/`pool-shelf`/tide-ledge platforms, or any `mirrors`/`receivers`/`springs` entries that Chapter 02's walkthrough section of this file describes in detail — the file in the repo right now is a much shorter, in-progress layout (a lockbox, a lensBox, a ladder wall, an exit trigger) that doesn't match that walkthrough at all. This was confirmed by reading the actual file and grepping the whole `world/` tree for `moonwell`/`pool`/`brink`/`tide`, not assumed. Since none of those objects exist in the current source, there was nothing to swap for them in this pass — if/when Selene's crater is rebuilt to match the documented walkthrough, the moonwell/pool fixed relay and rotatable pool will be `Mirror` instances (same geometry-touching restriction as the heliostat mirror applies) and the moon-dial will be a `hold: true` `Receiver` (eligible for the same swap-or-leave-primitive evaluation as Helios's sky receivers above).

## Physics constants (`core/`)

`SPEED 8`, `JUMP_VELOCITY 10`, `SPRING_VELOCITY 23`, `GRAVITY 26`, player half-extents `.5 × 1.1`, everything on the `PLAYER_Z_DEPTH = -4` plane. `Physics2D.js` is ported verbatim from *What the Snow Remembers* — read its `EPS` comments before touching either resolver; the two tolerances point in opposite directions on purpose.

Respawn: falling below `layout.deathY` (−15 in Helios, −44 in the crater) returns the player to the last platform they stood on (`Checkpoint` stores `platform.safeX`). Bridges, decks and **phase surfaces** are not checkpoint platforms, so the aerial route sets no checkpoint — falling off it returns the player to the hub.

## UI / Menu Flow

Landing → start → chapter select (Selene disabled until `helios-complete`) → play → pause (Esc) → **chapter complete** → play → ending. Plus a built-in **How to play** screen and a **"Where's the exit?"** button, which is now offered in both chapters but only once that chapter's exit has actually been revealed.

Landing pitch reads *"Two skies. Two unfinished instruments."* (was "One unfinished telescope") to match the magnifier/telescope copy split described in Premise above; `#selene-intro` reads *"The Helios magnifier cannot reach here. Find the moon lens and eyepiece for Selene's telescope."*; the `#fragments` HUD counter and its aria-label now say "instrument parts" rather than "telescope parts". The **How to play** guide screen is wrapped in a `.guide-board` div with one `.instrument-note` paragraph per chapter (Helios's heliostat/mirror instructions, Selene's phase-turning instructions) instead of one flat block of prose — `style.css` carries matching `.guide-board`/`.instrument-note` rules plus a landscape/short-viewport media query for it.

The HUD carries a **`#moon-phase` chip** in Selene. The phase is global state the player changed several screens ago and has to reason about before every drop, and the moon itself is off screen exactly when the answer matters most, so it cannot live only on the object.

### Language selection

`src/i18n.js` (new, modeled on the sibling `puzzle_game` repo's `src/i18n.js`) holds a `translations` object keyed by locale plus a `t(key, vars)` lookup with `{placeholder}` interpolation, and exports `getLocale`/`setLocale`. All 14 locales `puzzle_game` supports are covered (en, zh-Hant, zh-Hans, ja, ru, es, pt, pt-BR, fr, de, it, ko, hi, ar, th) with independently authored copy, not machine gibberish or English left in place — `zh-Hans` and `pt-BR` take the same shortcut `puzzle_game` does (`pt-BR` spreads `pt` with a handful of regional overrides; `zh-Hans` is authored directly rather than derived, since this game's key set is far smaller than `puzzle_game`'s). Locale persists in `localStorage['helios-selene.locale']`, falling back to `navigator.language` detection, then `en`.

There is a new `#language` **`.screen`**, reached the same way every other screen is (`data-show="language"`, delegated through the existing click handler) from both `#start` and `#pause`. Since it must not end the current run when opened mid-game, the click handler special-cases it ahead of the generic `data-show` branch that resets `state.playing`. It remembers whichever screen opened it (`languageReturnScreen`) and `data-language-confirm` returns there, so pausing to change languages and confirming lands back on `#pause`, not the main menu. The `<select>` applies the chosen locale immediately on `change` (no separate "apply" step) via `setLocale()` + `applyTranslations()`; the on-screen confirm button only closes the screen.

`applyTranslations()` is the single re-render point: every element carrying `data-i18n="key"` gets its `textContent` set from `t(key)`, `data-i18n-aria` sets `aria-label` the same way, and a handful of strings that need embedded markup (the landing pitch's `<br>`, the ending heading's `<br>`, the CC-BY credits line's link) are special-cased by id. It runs once at startup and again on every language change; dynamic HUD text (`#chapter-name`, `PARTS n / 2`, `MOON {phase}`, the locate-moon button's two states) already re-renders every frame or on its own state change, so it doesn't need a `data-i18n` hook.

Chapter `title`/`subtitle` and lockbox `hintLines` no longer live as English strings on the chapter data objects (`chapters/helios.js`/`selene.js`) — they're resolved through `t()` by chapter id (`t('helios.title')`, etc.) or by a `hintKey` field on each lockbox/lensBox (`hintKey: 'helios.lockboxHint'`) that `Lockbox.js` stores and `main.js`'s `showLockboxHint()` looks up via `t(box.hintKey)`. `Lockbox.prompt()` and `Mirror.prompt()` also now return `t('lockboxPrompt')`/`t('turnMirror')` instead of hardcoded English.

## VIVERSE integration

`src/viverse/ViverseSession.js` is a direct port of the sibling `puzzle_game` repo's implementation (same class shape, same `viverse-auth`/`viverse-leaderboard` skill contract, same release-blocking gotchas: `account.htcvive.com` as the auth domain, a 1200ms handshake delay after SDK detection, `accessToken`+`token`+`authorization` all passed together to `new sdk.avatar(...)`, and the leaderboard's `rank` field being 0-based rather than 1-based) — read that project's `.claude/skills/viverse-auth/SKILL.md` and `.claude/skills/viverse-leaderboard/SKILL.md` before touching this file. Don't reimplement the integration from the skill prose directly; port from `ViverseSession.js` instead.

- **App ID / leaderboard name** come from env, never hardcoded: `VITE_VIVERSE_CLIENT_ID` (`pd5vjemene`) and `VITE_VIVERSE_LEADERBOARD_SPEEDRUN` (`speedrun`), read via `import.meta.env` in both `ViverseSession.js` and `main.js`. `.env`/`.env.example` carry the real values (the client ID is a public app identifier, not a secret, matching `puzzle_game`'s own `.env.example`). `.env` is gitignored.
- **One leaderboard**, unlike `puzzle_game`'s two: `speedrun`, scored by total elapsed play time in seconds, ascending (fastest wins) — same convention `puzzle_game` uses for its own time-based boards. It must be created in VIVERSE Studio under this app's ID (API name `speedrun`, numerical, ascending) before testing — code changes alone don't create it.
- **The run timer** (`main.js`) is `performance.now()`-based: `startRunTimer()` fires only when Helios is entered fresh from chapter select (not when re-entering Selene via "Go on to Selene", so the two chapters share one clock across a full run), and `show()` calls `pauseRunTimer()`/`resumeRunTimer()` whenever the `#pause` screen's visibility actually changes, so paused time never counts toward the recorded time. `finishChapter()` snapshots `elapsedRunSeconds()` into `state.runSeconds` at the true ending (both chapters complete).
- **The "Use my VIVERSE avatar" button swaps the player model.** After auth, `ViverseSession.getActiveAvatarUrl()` reads `activeAvatar.vrmUrl` before its GLB fallbacks, and `Player.loadViverseAvatar()` loads that signed URL with `GLTFLoader` plus `VRMLoaderPlugin`. A bundled MIT-licensed `public/animations/idle.vrma` is retargeted with `VRMAnimationLoaderPlugin`/`createVRMAnimationClip` and plays whenever the avatar is grounded and still; the host game keeps its own normalized-bone walk/jump poses while it owns movement and collision. The loaded scene is made visible on camera layer 0, receives the same side-view scale/grounding/facing treatment as the traveler, and enables shadows without changing this game's host-owned physics. The default traveler remains active until the remote asset has loaded successfully, so an expired URL, CORS problem, or malformed avatar leaves gameplay intact. The connection label changes to `connectedAs` only after the model swap succeeds; login redirect resumption follows the same path.
- **Records screen** (`#records`, reached only from `#start`'s "See records" button) is new UI, not a port of `puzzle_game`'s bespoke two-page `#records` DOM — a single simple list (rank/name/time) built from this game's own `.screen` pattern. `loadRecords()` tries `fetchLeaderboardAsGuest()` first (viewable without logging in, same as `puzzle_game`) and only falls back to the authenticated `fetchLeaderboard()` if the guest read is empty and a session already exists.
- **Submit button** (`#ending`, "Submit my run") calls `ensureLogin()` if not already authenticated (may redirect to VIVERSE login — expected) then `submitScore('speedrun', Math.round(state.runSeconds))`. Guarded by `state.runSubmitted` so a duplicate click (or a re-render) can't double-submit the same run; the flag resets only when a fresh run actually starts (`startRunTimer()`, and `restartGame()`), per the leaderboard skill's idempotent-submit rule.
- **Login-redirect resume**: `viverseSession.resumePending()` is called once on module init (never eagerly on every boot — login is opt-in, triggered only by the avatar/submit buttons, same rule `puzzle_game`'s CLAUDE.md states for itself). It reads whatever pending payload survived the full-page redirect from `localStorage['helios-selene.viversePending']` and either re-fetches the profile (avatar case) or re-submits the score it was carrying (submit case) — the ending screen's own in-memory state doesn't survive a full navigation, so the resumed submit reports its outcome on the start screen's `#notice` instead of the (now-gone) ending screen.
- **Not verifiable locally**: `npm run dev`/`npm run build` confirm the code loads and builds with no console errors, but the actual VIVERSE SDK handshake, login redirect, profile fetch, and leaderboard read/write all require a real browser session against VIVERSE's live Studio/SSO backend — there is no local mock for any of it. Verify end-to-end only from an actual published/preview VIVERSE Worlds session.

## Known gaps still open

- The pit **safety-net spring fires on the intended descent too.** Its guard is `!state.lensCollected && !triangulation.lens.visible`, but the lens only becomes visible *after* the lens box is solved, and the box is at the bottom of the pit — so the spring is always already there when the player arrives, undercutting the "spring as reward for the lens" beat the comment describes. (The net itself works.) Selene sidesteps this entirely: its one spring is `revealed: true` from the start and framed as a marked way back, not a reward.
- **No wordless heat feedback on the burn.** `applyHeat`, `createFallingMass`, `updateGate` and `animateGate` in `LensGates.js` are exported but imported nowhere — the whole heat-ramp/toppling-rock system is dead code. The wall simply disappears after 1.15 s; only the reticle's charge bar moves.
- **HUD legibility**: dark HUD text sits over the pale bottom of the sky gradient. `#scope-label` and `#moon-phase` carry their own dark grounds; `#chapter-name` and `PARTS n / 2` still do not.
- Both sky receivers are **visible from spawn** and overlap the `01 / HELIOS` HUD label at the default camera position.
- `Triangulation` does no triangulation — it is a lens pickup, used for Helios's fire lens and Selene's eyepiece. Worth renaming.
- Selene's pool chain is **one degree of freedom**: the moonwell is a fixed relay pointed at the pool, so the only thing the player sets is the pool's angle. That is the same difficulty as Helios's heliostat tutorial, used at Selene's peak beat. A second rotatable pool in series is the obvious place to add difficulty if the chapter plays too easy.
- **`shade` is optional.** Setting the phase to `new` at the brink is the graceful way down; missing it just costs a longer fall to the same chamber. That is deliberately gentle, but it means beat 5 currently teaches the commitment idea without ever charging for it.
- **Observed but not fixed (belongs to the in-progress i18n/locale-selection work, not this art pass):** during verification of this pass's swaps, loading Helios threw `Cannot read properties of undefined (reading 'toUpperCase')` at `main.js`'s `document.querySelector('#chapter-name').textContent = ...chapter.title.toUpperCase()...`. `chapters/helios.js` no longer defines `title` (it's mid-refactor onto `src/i18n.js` lookups as of this writing), but that one call site in `main.js` hasn't been updated to match yet. ## Open / Not Yet Decided
